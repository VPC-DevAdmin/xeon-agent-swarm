Enterprise agents shift infrastructure toward the CPU

Enterprise agents perform CPU-intensive jobs between large language model (LLM) calls. Our Enterprise-style mix carried 143 resident agents per CPU on a 64-core Intel Xeon, requiring model-serving capacity equivalent to about 1.6 RTX PRO 6000 GPUs. Agent execution therefore needs a substantial CPU tier alongside model serving.

Agent workflows are shifting infrastructure toward the CPU

Agent workflows increase the CPU work performed for each model call. Tools and sandboxes retrieve records, process documents, analyze datasets, compile software, and validate results. These operations require CPU capacity throughout a workflow, including periods when the agent is waiting for its next model response.

Our Enterprise-style mix carried 143 resident agents per CPU, combining short service tasks with longer research, document-intake, analysis, and code workflows. The mix produced a 1:1.6 CPU-to-GPU ratio under the model-serving assumptions in Section 4. CPU jobs occupied the host while model calls supplied decisions and explanations.

Separating agent execution from model inference lets teams size each tier for its own work. In the illustrated deployment, PowerEdge R770 systems run the agents and their jobs, then send model calls to a PowerEdge XE7740. Agent execution can stay close to enterprise data while model serving runs where GPU resources are available.

1

The Enterprise mix fills the system with different kinds of work

Enterprise agent deployments carry a mix of work. Many agents handle short service tasks such as triaging requests and updating records. Alongside them, smaller groups research information, ingest documents, analyze business data, and change software. We represented this population with five archetypes that span those common activities.

We group the incoming work into a twelve-request tile: six task workflows, one research workflow, one ingestion workflow, two analyst workflows, and two code workflows. Repeating that tile keeps the incoming mix consistent. Longer jobs stay resident longer, so the population present at any moment has a different balance.

One resident agent represents one end-to-end workflow, including its planner and workers. A three-worker analysis counts as one workflow in the resident-agents-per-CPU total. The count includes workflows executing host jobs and those waiting for model responses or resources.

At 143 resident agents per CPU, the mix used 85 percent of the processor and about 355 GB of memory. The workflows required about 8.4 LLM calls per second and roughly 5,700 output tokens per second from the model tier. That demand corresponds to about 1.6 RTX PRO 6000 GPUs under the selected serving assumption. Sandboxed jobs, retrieval, agent execution, and supporting services contributed to the CPU work.

2

Five archetypes follow different paths through the agent flow

An agent uses a language model to decide how to pursue a goal. Its planner can assign a worker or divide the request into several jobs. The runtime connects those workers to data and sandboxes, which are isolated environments for executing software. Workers return results for review before the agent produces its answer.

The task agent handles a routed support ticket. It looks up relevant knowledge, records the action, and prepares a checked reply. Research assigns three workers in sequence, each preparing source text and retrieving evidence for a brief. These agents use the model to interpret evidence and write responses, while the host prepares that evidence and retains the work.

Other requests require a substantial processing job before an answer is useful. Ingestion reads supplied PDFs with optical character recognition (OCR), then prepares their text for search. The analyst profiles payment events, compares periods, and prepares report data. The code agent runs supplied software through optimized builds, continuous-integration (CI) checks, and incremental rebuilds. Each job returns an artifact the model can explain, such as searchable text, calculated metrics, or a test report.

3

Agent jobs determine CPU demand

The CPU performs the operations that turn an agent’s request into usable work. A model can request a comparison or a build, but the host must calculate the results or execute the software. Those operations consume CPU time and working memory before the agent can explain their outcome.

Document intake processes page images and text. Retrieval runs embedding models and scores candidate passages, a step called reranking. Analysis joins and sorts arrays, often making several passes over the same data. Compilers and tests execute in isolated processes, while the runtime schedules each worker and records its progress.

The benchmark uses supplied documents, data, and source trees with fixed job sizes. Parsers, models, databases, and compilers perform the stated work. Each operation returns an artifact needed by the workflow, such as clean text, calculated metrics, or a test report.

Complete workflows connect CPU work to model demand

Each archetype combines host operations with planner, worker, and review calls to the model. Task and Ingestion use one worker. Research, Analyst, and Code use three. Figure 5 totals the CPU work and model demand across a complete workflow.

One core-millisecond records one core working for one millisecond. CPU work adds across cores, so the total is not the workflow’s elapsed time. Two cores busy for one second account for 2K core-ms. The figures abbreviate 1,000 core-ms as 1K.

Agent weight divides a workflow’s CPU core-ms by its total required output tokens. It connects host work to the model tier’s decoding work, which generates those output tokens. Model serving also processes each call’s input context, called prefill. Section 4 states the serving throughput and cache assumption used for sizing.

4

How the Enterprise workload uses the server

The Enterprise mixture kept the 64-core processor at roughly 85 percent utilization while carrying 143 resident agents per CPU. Sandboxed jobs overlapped with retrieval, model waits, and agent execution, keeping the processor active across workflows with different lifetimes.

The test used a PowerEdge R470 with one Intel® Xeon® 6761P processor and 1 TB of memory. Four orchestration instances each ran a control process, 28 executors, and a PostgreSQL database. The same host ran the retrieval and embedding services that the workers called.

Capacity and system use

The count of resident agents per CPU includes every workflow that has arrived but not yet finished. Task agents complete quickly, while analysts and code agents remain active through longer calculations and builds. As the working population grows, those longer jobs increasingly overlap and their completion times rise.

The operating point of 143 resident agents per CPU sustained the Enterprise mixture with CPU utilization of 85 percent. Six physical cores served reranking, one served query embedding, and two served ingestion embedding. The remaining 55 cores ran agent execution, sandboxes, and supporting services. Retrieval and embedding retained headroom while longer jobs occupied the application pool.

The server used about 355 GB of memory at capacity, with peaks near 430 GB as jobs overlapped. Analyst arrays and intermediate calculations account for much of that working data. OCR also creates page images, while builds maintain source trees and temporary files. Memory sizing needs to accommodate those peaks alongside the shared services and agent runtime.

The response curve shows how completion times change as the resident population per CPU grows. At capacity, the code workflow’s 95th-percentile completion time was about six minutes, and the analyst’s was about nine. At the higher tested load, unfinished work accumulated because the host could no longer keep pace. Completion targets still depend on the task: a ticket reply and a software build need different time allowances.

The work inside each archetype

TaskResearchIngestionAnalystCode

Python, DeepAgents, and LangGraph ran the planner and worker sequence. The planner delegated each subtask, workers called the host services, and PostgreSQL retained their progress and results. Mechanical checks verified output structure, while model judgments reviewed the worker reports and final synthesis.

Each sandbox started a fresh isolated process with supplied inputs, no network access, and limits on CPU time, memory, and file size. The jobs ran single-threaded. Retrieval services used ONNX Runtime and Text Embeddings Inference (TEI) to embed queries and score passages. SQLite FTS5 provided text lookup. These operations performed the host work shown in the flows.

Task agent

The task represents a routed support ticket, such as an export arriving at the wrong local time after a timezone change. The planner assigns one worker, which requests a record operation. That operation searches the knowledge base, reranks the matches, and commits an audit record before returning to the worker.

The worker prepares the classification, severity, likely cause, and customer reply. A mechanical check and one model judgment review the response. The runtime then hands back that checked answer, so the revised workflow needs no sandbox or additional model turn to synthesize a single worker’s result.

Research agent

A research brief needs both readable source material and relevant enterprise evidence. The planner assigns research, analysis, and writing workers in sequence. Each worker parses 30 supplied HTML pages, performs three retrievals, and drafts a section for review.

Parsing removes navigation and boilerplate before the worker uses the source text. The retrieval path embeds each query, searches the passage corpus, and reranks 128 candidates. The CPU therefore prepares and selects evidence before the model writes, and the planner combines the three reviewed sections into a final brief.

Ingestion agent

Document intake makes supplied files searchable. The worker sends 50 PDF pages through rendering and OCR, then redacts personal-data patterns and prepares clean text chunks. Page images and extracted text stay on the host throughout this processing.

After the sandbox finishes, the executor requests embeddings and builds a temporary keyword index. A check query confirms that the index can return content. The worker records the intake result and summarizes it for review, followed by the planner’s synthesis and final validation.

Analyst agent

The analyst investigates payment-event volumes and anomalies through profiling, period comparison, and reporting. Its first job processes 100 million rows. The second compares two periods of that size, and the third performs another 100-million-row reporting pass.

These jobs join merchant attributes to events, aggregate volumes, and sort values to calculate percentiles. Rolling calculations and anomaly rankings add further passes over the data. NumPy performs the calculations inside the sandbox, leaving the model to explain the structured results. The first two workers retrieve schema and metric definitions before calculating, and each worker passes review before the next begins.

Code agent

The code agent runs a continuous-integration sequence over supplied Lua and SQLite source trees. A setup worker makes an optimized build and runs the suites. A second worker performs an instrumented build, tests it under the undefined-behavior sanitizer, and runs the compiler’s static analyzer.

The verification worker starts with a baseline build, touches two Lua source files, and rebuilds incrementally before running further checks. Each worker retrieves build guidance and starts a fresh sandbox. The compiler and tests produce the artifacts that the worker records and explains, while the planner combines the reviewed reports.

Model-serving requirement

Planner delegation, worker tool requests, drafted responses, and model judgments all contribute to the serving requirement. Across the measured resident population per CPU, those calls required roughly 5,700 output tokens per second. The host test reproduced recorded gpt-oss-20b responses and timing through a seeded endpoint, while the CPU executed the surrounding jobs and services.

GPU sizing uses 3,500 output tokens per second for gpt-oss-20b on one RTX PRO 6000 Blackwell Server Edition. That rate rounds down the published output throughput after a five-percent allowance for uncached prompt work and cache misses, assuming prefix caching. Dividing the per-CPU mixture’s output requirement by that serving rate gives about 1.6 GPU equivalents, which can be shared across a model-serving fleet.

5

Plan CPU capacity alongside model serving

Enterprise agents need CPU capacity for the work they perform around model calls. The tested mix supported 143 resident agents per CPU on a 64-core Intel Xeon 6761P, with CPU utilization of 85 percent. The processor carried short service tasks alongside longer processing jobs.

That mixture required model-serving capacity equivalent to about 1.6 RTX PRO 6000 GPUs per CPU under the gpt-oss-20b sizing assumptions in Section 4. The CPU performed the data processing and software execution while the model supplied instructions, explanations, and judgments. As these jobs occupy more of each workflow, infrastructure plans need a larger CPU tier relative to the GPUs serving model calls.

For deployment planning, resident agents per CPU should describe a defined mixture of work with acceptable completion times. A population dominated by short tickets places different demands on the host than one dominated by builds and analysis. Size the execution tier against that mixture and its working memory, then size model serving against the calls those agents require. Keeping the tiers separate also lets teams place agent execution near enterprise data and model serving where GPU resources are available.
