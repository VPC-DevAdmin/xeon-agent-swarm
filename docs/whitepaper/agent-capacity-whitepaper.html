5,000+ AI agents on one CPU server

One Dell™ PowerEdge™ R470 with a single Intel® Xeon® 6 processor and no GPU held more than 5,000 agents at once. Each agent was a planner, three tool-using workers, and a synthesizer completing a full task every few seconds. Every workflow type finished inside a 15-second deadline at least 95% of the time, at 95% confidence. The orchestration tier ran entirely on the CPU; model inference was replaced with deterministic, zero-latency responses, so the figure measures the orchestration host itself, not the model. The processor still had about a third of its cycles free when the software reached its limit.

Overview

One Dell™ PowerEdge™ R470 with a single Intel® Xeon® 6 processor and no GPU held more than 5,000 AI agents in flight at once. Each agent was a complete deep-agent workflow. A planner decomposes a task into three specialist subtasks, three workers each make a tool call and write a section, a synthesizer assembles the result, and every step is validated along the way. The agents ran continuously, starting a new task three seconds after finishing the last one, and every workflow type completed inside a 15-second deadline at least 95% of the time, at 95% statistical confidence.

The figure measures the orchestration host, not the language model. Model calls went to a stand-in router that returned deterministic canned responses with no generation time. The server was therefore doing what an agent host does between model calls: assembling prompts, dispatching tools, validating outputs, persisting every step to a database, streaming events, and enforcing budgets. That is the work a previous paper in this series argued belongs on the CPU tier. This paper measures how much of it one socket carries.

The method borrows from virtual-desktop and virtualization sizing. A fixed tile of three representative agent workflows is added one whole tile at a time, and sessions loop continuously in a closed-loop ramp. The reported capability is the highest session level at which every workflow type meets its deadline under a joint 95% confidence rule. Capacity was measured in two settings on the same box: a single orchestrator instance, which measured 2,094 agents before its control process saturated one core, and a fleet of four instances whose individual bests sum to 5,589, with more than 5,000 held at one moment. At those levels the processor had roughly a third of its cycles free; pressing further filled nearly every core, but the extra agents' answers came back late. Each ceiling before that one had been a software limit as well: a single-writer database file, a single-process event loop, a connection pool, a relay core. Section 5 lists them in the order this implementation met them; other stacks will meet the same categories at their own levels.

The numbers come from instrumented runs on the host on August 30 and 31, 2026. Every unit of work is recorded in a per-run evidence ledger. The published verdicts were produced by an offline judge that re-reads those ledgers under a versioned rule, so a verdict can be re-derived without re-running a test.

2

What an agent is, and what an agent host does

An agent is a language model run in a loop by a program. The program gives the model a goal and a set of tools. The model decides on a step, the program executes it and feeds the result back, and the loop continues until the model reports the task done or the program's budget runs out. A chatbot answers a question in one model call. An agent completes a task in many, and between the calls it searches, reads, writes records, runs tools, and checks its own work.

The agents in this test follow the deep-agent pattern, which is what production orchestration frameworks build. A planner reads the task and decomposes it into subtasks, then delegates each to a specialist worker with its own instructions and tool grants. Each worker runs its own bounded loop, calling a tool, reading the result into context, and writing its section. A synthesizer assembles the sections into one answer. A validator checks every worker output twice, first mechanically against the expected shape and then with a judge model, and a grader scores the final answer. A budget bounds the number of subagents and tool hops so a confused plan cannot balloon. Every step, attempt, and validation is written to a database as it happens, so the run can be inspected, audited, and resumed.

Most of that loop is not inference. Between model calls the host builds the next prompt from accumulated context and routes each call through a tier router with per-attempt headers. It dispatches tool calls and waits on their backends, runs the mechanical validator, writes step and attempt rows, relays live events to any watching client, and checks budgets. In a deployment the model itself may run on another server or on a GPU tier, which is why this series treats the orchestration host as a separate sizing question from the inference tier. A platform team choosing hardware for an agent control plane needs to know how many agents one host can drive, and that number is not derivable from tokens per second.

The count in this paper is of agents in that sense. One agent is one session running the full workflow in a loop. Each of those sessions spawns three worker subagents per task, so the number of subagents in flight is about three times the headline. The paper reports sessions rather than subagents because a session is the unit an operator provisions and a user waits on.

3

A tile of three agents, ramped until the deadline breaks

Capacity is measured the way virtual-desktop and virtualization benchmarks measure it. A fixed bundle of representative workloads, the tile, is the unit of load. The idea is no more complicated than counting how many same-size marbles fit in a jar: the marbles are standard-size agent jobs, the jar is the server, and marbles are added until answers start coming back late. The one wrinkle is that marbles take longer to settle as the jar fills, which is why the deadline, not the raw count, decides when the jar is full. The ramp adds whole tiles, so every level has the same workload mix and adjacent levels are comparable. Each session in a tile runs its workflow, thinks for three seconds, and runs it again, and the level climbs until the workflows stop meeting their deadline.

The tile holds three workflow types, each a self-contained brief with all of its source material inside the prompt. A research brief turns four field notes on CPU-only inference into a one-page recommendation. A comparison weighs INT8, INT4, and FP8 quantization from stated measurements and recommends one. A digest ranks four release notes by operational impact and writes five bullets. Each brief instructs the planner to plan exactly three subtasks, research, analysis, and writing, and each worker to call the record-keeping tool exactly once. Nothing in a workflow depends on the web, an external tool, or the model's appetite, so a unit's size cannot drift with conditions. Every prompt carries a deterministic seed-varying suffix so a prefix cache cannot quietly turn the test into a cache benchmark.

Two load models

The harness drives the tile two ways, and each answers a different question. The closed-loop ramp fixes the number of sessions, lets each one loop continuously, and steps the count up. It answers how many agents the host can keep in flight inside a deadline, which is the provisioning question. The open-loop generator schedules arrivals on a clock, independent of completions, and raises the offered rate. It answers how many workflows per second the host absorbs before a backlog starts to grow, which is the throughput question. A closed loop cannot run away, because a slow host slows its own sessions, so latency grows steadily past the knee rather than collapsing. An open loop can, and the harness watches the backlog with a bootstrap bound on queue growth and confirms any boundary in two separate windows at the same rate. The capability figures in this paper come from the closed-loop ramp. No version-14 open-loop number exists. A subsequent open-loop measurement at workload version 15, a heavier context-weighted mix, sustained about 450 workflows per second box-wide across four instances and was terminated by the host itself: 90% processor utilization with all 128 threads busy. That run, not this paper's closed-loop rate, is the throughput reference.

The deadline and the judge

An agent that finishes late has failed the person or pipeline waiting on it, so the pass criterion is a deadline, and the deadline belongs to the use case rather than to the machine. Six service tiers cover the range from an answer a person reads in-line to a job submitted and forgotten. A weigh-in at one tile measures each workflow type's median on the host, and the worst type's median places the host in a tier. Against the stand-in this host measured 4.4 to 4.7 seconds at one tile, which puts it in the conversational tier with a 15-second deadline. The rung was pinned for the fleet run so that four simultaneous weigh-ins could not nudge the fleet into a looser tier than the single instance.

Each bounded tier's deadline is three times its median ceiling, so a host at the top of its tier may slow threefold under load before it misses. The tiers are a reasoned starting point from the anchor system and will be revised once several servers have been characterized.

Capability at a level is one joint claim across the three workflow types. For each type the judge computes a one-sided Wilson lower bound on the on-time fraction, with the alpha divided by three so the joint claim holds at 95%. A level passes only when every type has enough decided samples and every lower bound is at or above 0.95. A level fails only when the evidence refutes passing, meaning a type's upper bound sits below the target. Between the two is silence, neither a pass nor a block, which is how a thin level with a handful of samples avoids either inflating or crushing the result. The ramp searches upward with geometric steps while the host has headroom, then refines between the last pass and the first fail down to one tile. The reported capability is the highest passing level below the first failing one. Stated precisely, the claim at that level is that each workflow type's on-time fraction is at least 95%, at 95% confidence jointly across the three types, for the units that level decided. The bound covers that level; picking the best of many tested levels, and run-to-run variation, are covered by the repeat series rather than by this bound.

What the stand-in does and does not remove

The test targets the agent host, so the inference tier is replaced by a stand-in router that speaks the same OpenAI-compatible wire contract as the production tier router. The stand-in classifies each request as a planner, worker, or judge call and returns deterministic canned responses that drive the real engine end to end. It adds no generation latency. The stand-in ran on the same server over loopback, eight worker processes per orchestrator instance. Its CPU is counted inside the box totals reported here, so the host was carrying the stand-in's request handling as well as its own work. A run is disqualified by what it hides, not by where its stand-in lived, and every result records the stand-in's location, worker count, latency distribution, and headroom arithmetic.

Removing model time changes what the number means. With a real model each workflow would take tens of seconds instead of one to seven, and a session would spend most of its life waiting on inference. The host's limit is a rate of workflows it can drive per second, and the session count follows from that rate and the length of a session's cycle. Section 6 works that arithmetic for a deployment.

Results: one instance, then four

Two configurations were measured on the same server on August 30 and 31, 2026. A single orchestrator instance with 96 executor processes measured 2,094 agents, with a median workflow time under two seconds and a rate near 350 complete workflows per second. A fleet of four complete instances, each with its own control process, 28 executors, database, and stand-in router, reached bests of 1,571, 825, 1,601, and 1,592 agents, 5,589 summed, and at its fullest single moment the server held 5,085 agents with at least 95% of answers on time in every instance. The processor was about two-thirds busy at those levels.

The fleet total is a sum of four separately judged instances, and the instances did not finish equal. They share the box, so each one's ramp is noise in the others' measurements, and the judge reports the highest passing level below the first level whose evidence refuted a pass. Instance 2 met such a level at 1,128 agents while instances 3 and 4 climbed past 1,590, and its certified figure of 825 is the last level it had fully proven beneath that point. The paper's headline is the load the server demonstrably held all at once, 5,085, rounded to 5,000-plus. The four instances' separate bests sum higher, to 5,589, but those peaks came minutes apart, and the per-instance split moves from run to run. The final protocol was then repeated three times with fresh seed draws. The box-level sums were 5,589, 5,047, and 5,268, a median of 5,268 with about 10% spread. The load held at one moment reached 5,085, 3,382, and 5,397: in two of the three repeats the server held more than 5,000 agents at once, and in the third, staggered instance peaks kept the maximum lower even though the summed bests stayed within 10% of the other runs.

Within an instance, the approach to the ceiling has a recognizable shape. On instance 1 the median workflow sat between 5.5 and 7.5 seconds from a few hundred agents to 1,167, with the 95th percentile under 9 seconds and every decided workflow inside the deadline. At 1,593 the median moved to 12.7 seconds, the 95th percentile reached 14.9, and 3.3% of workflows crossed 15 seconds, enough for the judge to refute the level. At 2,175 the median was 19 seconds and 60% of workflows missed. No workflow errored at any level in the fleet run. The ceiling arrived as lateness, not as failures.

The single instance told a different story at the top. Its median stayed between 0.8 and 2 seconds all the way to 2,175 agents, and its rate reached 375 workflows per second at 1,593 agents, at or above the fleet's box-wide 310 to 370. Yet it certified fewer agents. The two facts are consistent. A closed-loop session count is the host's workflow rate multiplied by the length of a session's cycle, and a fleet session's cycle ran 11 to 17 seconds where the single instance's ran 4 to 6. Slower workflows that stay inside the deadline hold more sessions in flight at the same rate. The deadline is what stops that from being a free lunch, and it is why the paper reports rate alongside the session count. For a host doing this kind of work the rate is the more portable number, and it was 300 to 375 complete workflows per second in both configurations. That is 3,000 to 3,750 model calls, 2,100 to 2,600 validations, and 900 to 1,100 durable tool records every second from one socket.

At the ceiling the hardware was not the constraint. Box-wide CPU across the 128 threads read 60 to 72% at the last passing levels of both configurations. In the fleet run that time was split among the executors, the four stand-in routers, the four control processes, and the databases. Memory was never a factor: roughly a tenth of the 1 TB installed was in use at the ceiling. In the single-instance run, what saturated first was one core: the control process that dispatches workflows and relays their events. The fleet exists because four control processes on four cores lifted that ceiling without changing the executors or the workload, which is the plainest demonstration in the data that the wall was in the software. The fleet's own limit was different in kind: pushing past its best levels drove 96 of the 128 threads over 85% busy, and the extra agents' answers simply came back late. The last slice of the processor is reachable, but only past the deadline.

A second measurement: heavier agents, pushed until the hardware quit

After the session-count runs, the workload was made heavier where real agents are heavy: context. In workload version 15 the three agent types differ by how much retrieved material they carry, the way a research agent working from hundreds of retrieved chunks differs from one writing a short digest. The researcher's prompt carries about 24,000 tokens of retrieval in labeled sections, the planner reads it all once, and each worker receives only its own section. Averaged across the mix, one workflow now moves about 85,000 tokens through the host's ten model calls.

The load model also changed, from waiting users to a conveyor: jobs arrive on a fixed schedule whether or not the server keeps up, and the schedule speeds up until something breaks. For the first time in this series, the thing that broke was the machine. The run ended on the benchmark's hardware rule, with the processor at 90% and all 128 threads busy.

Where the ceilings were

The 5,000-plus figure is the seventh ceiling this platform met on this server, and each of the six before it was a software limit reached with the processor mostly idle. The first certified result was nine agents, at 2% CPU. In this Python-based implementation the limits appeared in persistence, the process model, per-run bookkeeping, connection management, and the single-process control plane. Other stacks will meet the same categories at different levels, so this section names them by area rather than by fix.

Two instruments made those ceilings visible, and both belong in any agent platform's telemetry from the start. The first is per-component CPU attribution, which splits the box's busy time among the control process, the executors, the inference stand-in, sibling instances, and everything else. With that split a run can tell a saturated core from a saturated socket, and it can refuse to sell another tenant's load as capacity. The second is a profiler run at mid-ramp and again at the boundary, which is how the pool-bookkeeping wall was found under a CPU figure that looked comfortable. A platform that reports only host-wide utilization will read 35% busy and conclude it has headroom while its one relay core is pinned.

One open item remains in the fleet data. From about 132 agents per instance upward, a growing share of workflows took roughly four seconds longer than the rest. That moved the instance median from about 1.3 seconds to about 5.5 and held it there to 1,167 agents. The single instance showed no such step. The candidates are the per-instance database containers, the stand-in's worker pool under four times the request load, and a retry with a fixed backoff somewhere in the path. It is the next thing to profile, and it matters to the reading of the headline, because the longer cycle is part of why the fleet held more sessions at a lower rate.

Reading the number for a deployment

The host's limit is a rate, and the session count follows from the rate and the length of a session's cycle. On this server the rate for workflows of this shape was 300 to 375 per second in both configurations, and a later open-loop measurement under a heavier context-weighted workload sustained about 450 workflows per second before the processor itself saturated, so the arithmetic below rests on a measured, hardware-bounded rate rather than an observed closed-loop one. In deployment each workflow also waits on a real model, so the cycle lengthens and the same rate supports proportionally more sessions in flight. Past some count the inference tier, not the host, sets the pace.

The arithmetic is direct. A session's cycle is its workflow time plus its think time, and the number of sessions in flight equals the completion rate multiplied by that cycle. With the stand-in the cycle ran 4 to 6 seconds on the single instance and 11 to 17 on the fleet. At 310 to 375 workflows per second those cycles give 1,900 to 5,300 sessions, which brackets the 2,094 and 5,589 measured. Replace the stand-in with a model tier that adds 20 seconds of generation across a workflow's ten calls and the cycle becomes 24 to 37 seconds. At the same rate that cycle corresponds to 7,400 to 11,500 sessions in flight before the host reaches the ceiling it met here. Memory at about 3 MB per session would be a fraction of the 1 TB installed. Whether the inference tier can serve 3,000 model calls per second is a separate sizing question with its own paper, and in most deployments it will bind first. The point of the measurement is that the orchestration host will not.

What the number does not say

The measurement is of one host, one fixed workload mix, controlled tool backends, and a co-located inference stand-in. The fleet figures come from a three-run repeat series with fresh seed draws each time, reported above with its spread; the single-instance figure remains a single instrumented run. The measurement also does not cover multi-node coordination, production third-party tool backends, long-duration soak behavior, or recovery after overload, and the per-instance split within the fleet moves from run to run. A different agent framework with heavier per-step work would meet the same categories of ceiling at different levels. The integrated-node case, where a 30-billion-parameter model runs on the same socket as the orchestrator, is a different measurement with workflows that take minutes rather than seconds, and it is not this paper's subject.

The claim that holds across those caveats is the one in the hero. A single-socket server with no accelerator drove thousands of complete agent workflows at once with a third of its processor idle. Every ceiling it met on the way was a software limit a platform team can move, and the follow-up throughput measurement closed the arc: with the software walls moved, the same server was finally stopped by its own silicon, every thread busy.
