White paper

40 agent workflows a second, with retrieval and real tool execution, on one CPU server

One Dell™ PowerEdge™ R470 kept pace with 40 complete agent workflows per second across five kinds of agent: researchers that search and rerank a 120,000-passage store, analysts that run sandboxed data jobs, summarizers, and short-lived task agents that are born, do one thing, and die. Every model call waited like a real API call.

The number is the cliff: offer more and the backlog grows no matter what deadline is chosen. Under an interactive promise of 45 seconds the server certifies 32 workflows per second with about 1,000 agents resident; under a responsive promise of 150 seconds, 40 per second with about 1,260. All three come from one measured curve, certified three times under different seeds.

01

One curve, three numbers

The benchmark offers work to the server at a fixed rate, holds it there for ten minutes, and reads what happens to workflow times. Repeated at rising rates under three different seeds, that produces one latency curve per archetype, and the three headline numbers are read off it: where it stays flat, where it crosses a deadline, and where it breaks.

Up to 32 workflows per second nothing moves: every archetype finishes in the same time it takes on an idle server, to the second, and not one of 109,000 admitted workflows at that level failed. At 40 per second the server still keeps pace, but the two archetypes that retrieve context queue for it and their tails leave the 45-second interactive line, while the digest and the task agent do not move at all. Above 40, completions stop growing: offer 44 or 48 and the server delivers 37 either way, the backlog climbs, and every archetype's time explodes, including the ones that need neither retrieval nor execution. That is the cliff, and it is the same in all three series to within half a percent.

Reporting the curve rather than a single number is deliberate. A capacity claim depends on the deadline behind it, and a lenient enough deadline can be made to say almost anything. The cliff cannot: it comes from arrivals outrunning completions, which no deadline choice affects. A reader picks the line that matches their use case and reads their rate; the cliff is the ceiling for everyone.

02

Five archetypes, each isolating one kind of work

An agent host does five kinds of work around the model: it orchestrates (plans, dispatches, validates, records), it retrieves and packs context, it executes tools, it carries the state of every session waiting on a model, and it does all of that for agents that live seconds as well as agents that live minutes. The workload is built so that each of those costs shows up in the data on its own.

Every workflow is one complete job through the production orchestrator: a planner delegates the declared subtasks to specialist workers, each worker calls its tools and drafts its section, a synthesis step combines the results, mechanical and judge validations check every step, and everything is written durably. Each archetype declares exactly how many workers, model calls, validations, and tool calls a finished unit contains, and any unit outside its contract is thrown out as invalid rather than counted either way, so higher load cannot quietly shrink the work performed.

Why these five. Retrieval appears three times, once, and never across the researcher, comparison, and digest; execution appears three times heavy, once light, and never across the analyst, comparison, and the rest; the digest carries orchestration alone, as the control; the task agent carries the fixed cost of an agent's life with almost nothing between its birth and its death. Each row differs from every other in at least one count, so the plateau data identifies every cost term, and each is a role an enterprise actually deploys.

The tile. Load is offered in tiles of six sessions: one of each of the four larger archetypes and two task agents, because short-lived agents are most of any deployment. The weight is a declared assumption. The cost of each component is published in section 7 so a reader with a different mix can rescale the result.

What retrieval does. A retrieving worker runs a BM25 keyword search over a seeded 120,000-passage store on the server, fuses that ranking with the answer of a vector index (modeled as a 15 ms off-server call, since a large vector database is its own system), prefilters to sixteen candidates, scores those sixteen with an INT8 cross-encoder on the processor's AMX units, and packs about 6,000 words of winning passages into its context with citations it then uses. Sixteen is a declared depth with a published cost law; retrieval quality is reported as a diagnostic and never judged, because reranking sixteen relevant passages costs what reranking sixteen irrelevant ones costs.

What execution does. An executing worker runs one job in a fresh, isolated interpreter with CPU, memory, and file limits and no network: an analyst's pass over a seeded day of payment events, joining, bucketing, computing per-merchant percentiles by sorting, rolling load, tail quantiles, and anomaly scores, and returning a few hundred characters of results into its context. Light jobs cost about 0.3 core-seconds, heavy about 1.4, interpreter start included. It is representative work with a stated size, not a load generator.

Every model call waits like a real API call. A deterministic stand-in answers through the production request path and waits per its payload: 500 ms to first token, 100 generated tokens per second, 8,000 prompt tokens per second read, with seeded jitter. A planner re-reading 30,000 tokens waits several seconds; a verdict waits about one. Each call re-sends its full context and is charged for all of it, which is pessimistic relative to a serving tier with prompt caching and is kept because the host's cost does not depend on the tier's cache policy.

03

How the server is packed

Four complete orchestration instances share the server, each with a control process, 28 executors, its own database, and its own model stand-in. Beside them runs the retrieval tier the workflows call, and the executors spawn sandboxed jobs as their workers need them.

The 64 physical cores are divided by whole core, read from the processor's topology, never as ranges of hardware threads: 14 cores for the reranker with one runtime thread per core (two threads on one core's siblings were measured to halve each other), 2 for the embedder, and the remaining 48 for the instances, executors, stand-ins, databases, and sandboxed jobs, pinned there so nothing shares a core's matrix units with the tier. The split is set from measured costs so both sides saturate near the same rate, which is what makes the server, not an allocation, the limit.

04

Finding the knee and the cliff

The load generator is open loop and deliberately dumb: it submits workflows on a fixed schedule that ignores completions, holds one rate for the whole run, and reacts to nothing except two safety stops. Overload therefore shows up as what it is, a growing backlog, rather than being hidden by a driver that slows down.

Rates are run as separate plateaus, one per fleet start, because workflow times of tens of seconds to minutes rival any level's dwell: a cohort admitted at one rate would otherwise finish under the next. Ten-minute holds let every cohort complete under the rate that admitted it. Exploration with five-minute holds finds the band between the last flat plateau and the first collapsing one; certification repeats the bracketing rates under three seeds with ten-minute holds; then one or two levels above the last keeping-up rate are run under the same seeds so the cliff is a measured level with a failed level above it.

Judgment happens after the run, from the per-unit evidence: every workflow's type, admit time, completion time, outcome, and offered rate, plus the workflows still running when the plateau stopped, which are kept as censored arrivals. A plateau sustains a deadline tier when every archetype's on-time fraction clears 95% at 95% confidence jointly, the backlog did not grow across the plateau, and the generator delivered at least 95% of what it was asked to. Resident sessions follow from Little's law at any stable point. The judge is versioned, and a rule change is applied to history by re-judging stored ledgers, never by re-running load.

06

What limited it

Two different things happen on the curve, and they have different causes.

The cliff is the server's cores. Past 40 workflows per second the executors' 48 cores are full in physical terms: the sandboxed jobs alone occupy 56 to 59 percent of all hardware threads, both threads of nearly every executor-side core are busy, the host reads 89 percent, and the generator itself starts shedding arrivals. Every archetype's time explodes, including the digest and the task agent, which need neither retrieval nor execution; that uniform collapse is the signature of CPU starvation rather than of any one component queueing. Delivery falls to 37 per second because a starved server does less useful work than a busy one.

The knee is retrieval. Between 32 and 40 per second the researcher's median goes from 34 to 48 seconds and the comparison's from 31 to 36, while the digest, the task agent, and the data analyst do not move. 07

Cost laws: the sizing tools

A single rate is only true for one mix. Each component's cost was measured on the fleet so the result can be rescaled to a different mix, a different rerank depth, or different job sizes.

ComponentMeasured costHow it enters the rate
Sandboxed executionlight job ~0.3 core-seconds, heavy ~1.4; about 0.82 core-seconds per tile-weighted workflow at the reference mixlinear in jobs per workflow; the executors' 48 cores are the budget
Rerankingabout 35 scored pairs per physical core per second (sixteen-pair calls of ~125 tokens); about 0.3 core-seconds per tile-weighted workflowlinear in candidates per call and calls per workflow; the tier's cores are the budget
Orchestrationa fixed floor of about 17 hardware threads across four instances, nearly independent of rate, plus a small per-workflow costsubtracted from the executors' budget before jobs are counted
Model tier (outside the server)about 20,000 prompt tokens and 1,300 generated tokens per workflow at the reference mix0.8 million prompt tokens per second at 40 workflows/s, across ~1,300 concurrent sessions

The reranker's law was checked directly: at sixteen, thirty-two, and forty-eight candidates per call, the last rate the tier sustained sat on the pair-budget line within a few percent, with the level above it failing each time. Passage length enters the same way as depth. A workload that reranks more, or executes more, lands lower in proportion; one that does less lands higher. The published rates are for the declared mix, sixteen candidates, and the two job sizes; the laws are for everything else.

08

The capacity figure applies to a defined test boundary

The benchmark establishes a practical starting point for this server as an agent host. It does not predict every production agent workload; mix, retrieval depth, job size, model latency, validation policy, and operating headroom all move the boundary, and the cost laws say by how much.

Included in the measurement

  • One Dell PowerEdge R470 with one Xeon 6761P processor, no accelerator
  • Four complete orchestration instances with 28 executors and one PostgreSQL database each
  • Five archetypes in a six-session tile: planning, workers, synthesis, validation, durable records
  • Real keyword search, rank fusion, INT8 cross-encoder reranking on AMX, and context packing on the server
  • Real sandboxed tool execution: isolated, limited, network-free jobs over seeded data
  • Modeled API-class model waits computed per call from actual payloads
  • Three series under different seeds, ten-minute plateaus, offline judgment, the cliff measured

Outside the measurement

  • Real model generation and provider capacity (latency is modeled; the model tier's own limits are not)
  • The vector index itself (its 15 ms answer is modeled; a large vector database is a separate system)
  • Retrieval quality and job correctness beyond determinism: reported as diagnostics, never judged
  • Production third-party tool services, multi-node coordination, failover
  • Long-duration soak and recovery after overload
  • Mixes, depths, and job sizes other than the declared ones, which are covered by the cost laws rather than certified

How to use the result. Pick the promise that matches the use case and read its row: 32 workflows per second and about 1,000 resident agents for interactive work, 40 per second and about 1,260 for work a person checks on within a few minutes, and 40 per second as the ceiling for anything. Rescale with the cost laws for a different mix, then apply production headroom and validate the intended model and tool set before deployment.

09

The result can be traced to versioned evidence

Every submitted workflow produced an evidence record with its type, arrival time, completion time, outcome, and offered rate, including the workflows still running when a plateau stopped; every two seconds the ledger also recorded host CPU, memory, and CPU by component. The versioned plateau judge recomputes every number in this paper from those records.
