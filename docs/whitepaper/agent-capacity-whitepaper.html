Chat serving places most compute on the GPU, so one orchestration host can support four to eight GPUs. One Dell™ PowerEdge™ R470 carried 152 resident agents across a fixed mix of five Enterprise capabilities.

Agent workflows are shifting infrastructure toward the CPU

Agent workflows are shifting the balance of AI infrastructure toward the CPU. Tools and sandboxes retrieve data, process documents, analyze datasets, compile software, and validate results between LLM calls. This increases the CPU capacity needed for each GPU system.

We tested this effect with an Enterprise-style mix of 152 resident agents, ranging from small task agents through research and ingestion to heavy analyst and code agents. The mix produced a 1:1.5 CPU-to-GPU ratio. Data jobs, software builds, retrieval, embedding, and validation kept the CPU active, moving the system away from GPU-heavy ratios associated with simpler LLM requests. A near-parity deployment would pair three dual-socket PowerEdge R770 systems with one eight-GPU PowerEdge XE7740, providing six CPU sockets for eight GPUs.

The deployment separates agent execution from model inference. The R770 systems run the agents, tools, and sandboxes, then send LLM calls to the XE7740 for model serving. Each tier can scale independently as demand changes. Agent execution can stay close to users and enterprise data, while model serving runs where power, cooling, and GPU capacity are available.

1

The Enterprise mix fills the system with different kinds of work

Enterprise agent deployments carry a mix of work. Many agents handle short service tasks such as triaging requests and updating records. Alongside them, smaller groups research information, ingest documents, analyze business data, and change software. We represented this population with five archetypes that span those common activities.

The mix is organized as a 12-agent tile: six task agents, one research agent, one ingestion agent, two data analysts, and two code agents. The system fills by repeating the tile, keeping the proportion of lightweight and intensive work consistent as the resident population grows. At the 151-agent point, the host carries many small workflows and a smaller number of long-running workflows at the same time.

The load changes as the mix moves from short tasks to deeper work. Task agents keep the runtime and its database active, while research and ingestion bring retrieval, embedding, memory traffic, and storage into the execution path. Data analysis and code workflows then add long sandboxed jobs for processing, compilation, and validation.

Together, the mix ran on one 64-core processor, reaching 76 percent host CPU utilization and using 39 percent of memory capacity. The agents issued 10.8 LLM calls per second, driving a model-serving requirement of roughly 5,200 output tokens per second. That demand corresponds to one RTX PRO 6000 GPU. The CPU profile shows how agent execution, sandboxed jobs, retrieval, embedding, and supporting services combine as the system fills.

2

Five archetypes follow different paths through the agent flow

An agent is the part of an application that decides how to pursue a goal. It uses a large language model to interpret the request, form a plan, and reason over results. The runtime connects the agent to enterprise data and isolated sandboxes when the job requires them. The agent then reviews the work and decides whether the goal is complete.

The Enterprise mix applies that pattern to five recurring forms of work. A task agent follows the shortest path. It understands a service request, generates a response, and validates the result. If the response fails the check, the agent returns to generation. It does not create a plan, retrieve more context, or run sandboxed work. A research agent plans its lines of inquiry, retrieves and reranks evidence, generates a brief, and validates the result. Retrieval supplies its evidence directly, so the research path does not need a sandbox.

Ingestion, analysis, and code agents retrieve their working material and send processing into sandboxes. The ingestion agent collects incoming reports, reads them with OCR, redacts personal data, removes duplicate content, creates embeddings, builds a search index, and checks the result. The analyst retrieves a week of service events, then divides profiling, anomaly analysis, and report writing across three workers. The code agent retrieves the working tree and build output so three workers can build the software, inspect failures, make a change, and run the tests again.

Together, the archetypes represent service operations, knowledge work, content onboarding, business analysis, and software delivery. They span short and long workflows, structured and unstructured data, direct record updates, retrieval, and CPU-intensive jobs. That range is what makes the mix useful for showing how enterprise agents place different demands on the same system.

3

Agent jobs determine CPU demand

Agent hosts carry out the work defined by an agent's plan. The host schedules workers, records state, retrieves evidence, processes documents, runs sandboxed jobs, and validates results.

The five archetypes map to functions found in enterprise operations. The task agent triages a support case, records its decision, and prepares a customer response. Research searches internal knowledge and assembles a brief from retrieved evidence. Ingestion prepares new documents for search. Analyst and code agents process operating data and test software builds.

Each CPU-intensive step produces an artifact that the workflow needs. Research parses 90 source pages and reranks evidence from a 120,000-passage corpus nine times. Ingestion reads 50 PDF pages with OCR, redacts personal data, and converts them into searchable chunks. Analyst jobs calculate merchant volumes, percentiles, and anomalies across 100 million payment events and compare the period with the last. Code jobs compile Lua and SQLite, run their project and integration tests under a sanitizer, and run static analysis.

The benchmark fixes these inputs before load testing and repeats the same work as arrivals increase. Parsers, embedding models, databases, compilers, and test suites perform the stated jobs. No synthetic CPU loop pads the workload. One core-millisecond records one processor core working for one millisecond. The figures abbreviate 1,000 core-ms as 1K.

Complete workflows connect CPU work to model demand

Each archetype combines its primary CPU job with a defined agent flow. Task and ingestion workflows use one worker. Research, analyst, and code workflows use three workers. Depending on the archetype, one workflow makes 4, 5, 13, or 16 model calls.

Each model call sends workflow context to the model tier and returns a decision or generated result. Repeated calls add prefill traffic. Output tokens determine the required decoding work.

Agent weight measures CPU core-milliseconds per required output token. The calculation divides the workflow's total core-ms by its output tokens. The denominator matches the GPU throughput used later in the paper, which is reported in output tokens per second.

Task agents require 0.5 core-ms of host work per output token. Ingestion agents require 30 core-ms. At capacity, the measured Enterprise mix requires 9.2 core-ms per output token.

4

How we built and ran the Enterprise workload

The test reproduced the full agent execution environment on one PowerEdge R470 while keeping model inference outside the measurement. We fixed the Enterprise mix and each job size before load began. The generator then raised arrivals in held steps until the server stopped finishing work as quickly as it arrived.

4.1One server ran the agent environment

The R470 used one Intel® Xeon® 6761P processor with 64 physical cores and 1 TB of memory. Four separate orchestration instances shared the host. Each instance ran one control process, 28 executors, its own PostgreSQL database, and the same production workflow path.

The host also ran the reranker, query embedder, ingest embedder, and fresh sandboxes created by the workflows. We assigned 51 cores to orchestration, databases, and sandbox jobs. The remaining 13 cores handled reranking and embedding. Whole-core placement kept those services from competing for the same processor units.

A deterministic endpoint returned seeded responses with remote model timing and token counts recorded from gpt-oss-20b. Each call included time to first token, prompt processing, output generation, and timing variation. Its CPU use remained inside the host total, though no model inference ran on the R470.

4.2Sandbox jobs performed fixed, recognizable work

Every arrival repeated the same declared job for its archetype. Research fetched and parsed 90 source pages in a sandbox, queried a 120,000-passage corpus nine times, and reranked 128 candidates for each query. The task agent looked the ticket up in the knowledge base, wrote one durable record, then generated and checked its response without entering a sandbox. Code and analyst agents searched the codebase or pulled definitions before each job, on the host's own retrieval services.

Ingestion rendered 50 PDF pages, read them with OCR, redacted personal data, removed duplicate text, and produced the chunks for embedding and indexing. Each analyst ran three jobs over 100 million payment-event rows, the second over two periods. Each code agent completed setup, CI, and verification steps over Lua 5.4.7 and SQLite 3.50.4.

Every sandbox started a fresh isolated process with fixed inputs and no network access. CPU-time, memory, and file-size limits bounded the job. Single-threaded execution also prevented one workflow from taking the entire server.

4.3Active agents connect capacity to incoming work

At 0.84 new workflows per second, the server accepted about 3,000 requests per hour. Each archetype stayed active for a different length of time, leaving an average of 152 agents on the server at once. Short task agents came and went while analyst and code agents remained inside longer jobs.

The active population settles when the server finishes work as quickly as it arrives. At 0.96 workflows per second, about 3,500 requests entered each hour. Heavy workflows then accumulated, so the agent count kept rising instead of finding a stable level.

We held each arrival rate for 25 minutes and repeated it under three timing seeds. The generator submitted new work on schedule without waiting for earlier work to finish. Open-loop submission exposed the point where a busy system became a growing queue.

4.4CPU work per model token sets the hardware ratio

The Enterprise mix used 9.2 core-milliseconds of host work for each output token required from the model tier. For planning, we used 3,500 output tokens per second per RTX PRO 6000 Blackwell Server Edition: a published measurement of gpt-oss-20b served through vLLM at 50 concurrent requests (4,378 tokens per second), adjusted for the context this workload's calls carry.

At that model throughput, one GPU corresponds to 32 busy CPU cores around its calls. The server's 48.4 busy cores at capacity are 1.5 times that requirement, giving 1.5 GPUs per socket. The ratio links a named Enterprise mix to a named model and accelerator.
