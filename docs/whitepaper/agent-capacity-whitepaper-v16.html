White paper

2,000 AI agents doing real retrieval on one CPU server

One Dell™ PowerEdge™ R470 sustained 62.7 complete agent workflows per second, about 226,000 an hour, while holding roughly 2,000 agent sessions in flight. Every workflow earned its own context on the server: keyword search over a 120,000-passage store, fusion with a vector index, and a neural reranker running on the CPU's AMX units. Every model call waited like a real API call.

The number was certified three times under different seeds and agreed to within 0.3%. What stopped it climbing was the server's own cores: at the certified rate the reranker's 40 cores were within a few percent of their measured ceiling and the other 24 were about three-quarters busy, 57 of the 64 physical cores in use, and the next load step overran the reranker.

01

The server completed 62.7 retrieval-backed workflows per second, three times over

Three independent series, each holding the fleet at five load levels for ten minutes apiece, certified the same top level: 62.7 complete workflows per second box-wide, with completions keeping pace with arrivals, every workflow type finishing inside 45 seconds at least 95% of the time at 95% confidence, and not one failed workflow among the 109,000 admitted at that level. The three series agreed to within 0.3%, so the figure is a measurement rather than a lucky run.

Every workflow did the work a production agent host does before its workers can answer. Its research workers searched a 120,000-passage document store on the server, fused that ranking with a vector index, reranked the sixteen best candidates with a neural cross-encoder on the CPU, packed the winners into their context, and cited them. Only then did the model calls happen, and each of those waited like a real API call, its wait computed from the tokens it actually carried.

At the certified rate the server carried about 2,035 agent sessions at once. The next load step, 72 workflows per second offered, was not sustained: research workflow times tripled and the backlog grew, because the reranker's cores had nothing left to give. That is the hardware speaking, and it is the reason this paper reports one number rather than a ramp that ran out of software first.

02

One agent repeatedly completes a defined workflow, and earns its own context

An agent session represents one user or process that submits a job, receives the result, pauses for three seconds, and submits another. A workflow is one completed job, held to a fixed work contract so that higher load cannot quietly reduce the work performed.

Each workflow uses a planner, three specialist workers, synthesis, validation, and durable records. What is new in this version is where the workers' source material comes from. Earlier versions handed each workflow its context inside the prompt. Now the workflow retrieves it: a worker calls the server's retrieval tool, which runs a BM25 keyword search over a seeded 120,000-passage store, fuses that ranking by reciprocal rank with the answer of a vector index (modeled as an off-server call, because a large vector database is its own system in any deployment), prefilters to sixteen candidates, scores those sixteen with an INT8 cross-encoder on the processor's AMX units, and packs about 6,000 words of winning passages into the worker's context with citations. The worker's answer cites the passage ids it was given, so grounding is checkable.

The three workflow types differ by how much context they earn. The research brief retrieves in all three of its workers. The comparison retrieves once. The digest only records. Every worker also makes one durable record write. The contract below is enforced per workflow; a unit outside it is thrown out as invalid, never counted as a success.

Every model interaction waits like a real API call. The stand-in computes each call's wait from its payload with three published serving-tier parameters: 500 ms to first token, 100 generated tokens per second, and 8,000 prompt tokens per second read. A planner re-reading 30,000 tokens waits several seconds; a verifier returning a verdict waits about a second. Nothing is hand-assigned per stage.

03

The benchmark packed three workflow types across four instances and one retrieval tier

One load unit contains one research brief, one comparison, and one digest. Adding complete units preserves the same mix at every rate.

Four complete orchestration instances shared the server, each with one control process, 28 executor processes, its own database, and its own deterministic model-response router. Beside them ran the retrieval tier the workflows call: an embedder and the INT8 reranker, served through ONNX Runtime with dynamic batching. The server's 64 physical cores were divided by whole core, read from the processor's topology: 40 cores for the reranker with one runtime thread per core, 4 for the embedder, and the remaining 20 for the four instances and everything else, pinned there so no executor shares a core's AMX units with the tier.

The load generator held each offered rate as a plateau: a fixed arrival schedule that ignores completions, kept for ten minutes so that every workflow admitted at a rate finished under that rate. Five plateaus per series, 4, 8, 12, 14, and 16 workflows per second per instance, then a sixth at 18 to show the level that does not hold. Each series ran under its own seed; the certified figure is the median of the three.

All of the judging happens after the run, from the per-unit evidence records, under a versioned rule. A plateau qualifies for a service tier when every workflow type's on-time fraction clears the joint 95/95 bound, arrivals minus completions did not grow across the plateau, and the generator delivered at least 95% of the rate it was asked for. The reader needs to know that all three workflow types had to pass together, in every series.

Workflow times did not move from the lightest plateau to the certified one: the research brief's median stayed at 34 seconds and its 95th percentile went from 35 to 40. That flatness is what a sized system looks like below its limit. The reranker column is demand over measured ceiling: each workflow makes 1.33 rerank calls on average, and the tier's ceiling on 40 cores was measured at about 92 calls per second, so 62.7 workflows per second is 84 calls per second, 91% of it. The busy-thread column is what a monitoring tool would show and understates the server, for the reason given in section 5. The step to 18 per instance, run under the same three seeds, is where the tier ran out: the research brief's median went to 82 seconds and its 95th percentile to 189, the comparison's to 43 and 122, no tier's bound held, and the fleet delivered only 60.8 workflows per second against the 72 offered. A certified level with a failed level one step above it is a measured boundary, not a lower bound.

05

The reranker's cores are what limited it

At the certified rate the server's physical cores were 90% used: the reranker's 40 cores at 91% of their measured ceiling, the embedder's 4 lightly, and the other 20, carrying four orchestration instances, their databases, and their model routers, at 72% measured occupancy (71% of their hardware-thread capacity). A monitoring tool reads the same moment as 61% because it counts hardware threads, and the reranker deliberately leaves each of its cores' second threads idle: two runtime threads on the same core were measured to halve each other, so a saturated reranker core is fully used with one thread busy.

The core figures come from a dedicated 16-per-instance plateau (seed 7501) sampled per hardware thread every five seconds, taking each core as busy as its busier thread and the median over the plateau's middle: reranker cores 99% occupied, embedder 80%, the other twenty 72%, 90% of the 64 cores overall, while the same samples read 59% of hardware threads. The reranker's cost was measured directly and did not depend on how it was arranged: about one physical core for every three rerank calls per second, each call scoring sixteen passages of about 125 tokens, however the work was split across processes and threads. At 62.7 workflows per second the workflows make about 84 rerank calls per second, which is 28 cores' worth of pure scoring plus the batching, tokenization, and serving overhead that fills the rest of the 40. That arithmetic, not a guess, is why the allocation is 40 cores and why the next step fails.

Three software limits were found and removed on the way to this result, and the paper reports them because a reader sizing a system will meet them too. A queue in front of the reranker refused calls its cores could have served. An admission gate in each executor queued retrievals for tens of seconds while the tier answered in three. And the reranker's own runtime, when given a range of logical CPUs instead of whole physical cores, shared its cores' AMX units with unrelated work and delivered a third of its benchmark. Each was fixed, and each fix is in the versioned code behind this result.

Two totals fall out of the records for sizing the model tier behind this host. A completed workflow moved about 27,000 tokens on average through its model calls, 35,000 for a research brief, and generated about 1,700. At the certified rate the model tier would absorb about 1.7 million tokens per second and generate about 107,000 tokens per second across roughly 2,000 concurrent sessions.

06

Rerank depth is the dial, and here is its law

The certified rate depends on one declared choice: how many candidate passages the reranker scores per retrieval, sixteen in the reference workload. That number is not special, so the paper measures how the rate moves with it and publishes the rule instead of hiding the choice.

The tier's ceiling is a pair budget: about 1,300 to 1,400 scored pairs per second on its 40 cores, whatever the depth. A workflow averages 1.33 rerank calls, so the sustainable rate is roughly 1,300 divided by 1.33 times the depth. At sixteen candidates that predicts 61 workflows per second, and 62.7 was certified. To check the rule rather than assume it, two more depths were run at their predicted edges under one seed with five-minute holds.

The reference depth is at the lean end of practice: forty fused candidates, prefiltered to sixteen by a keyword scorer, twelve kept. A deployment that reranks more, or longer passages, lands lower in proportion; one that reranks less lands higher. The rule, not the reference point, is the sizing tool.

07

The capacity figure applies to a defined test boundary

The benchmark establishes a practical starting point for this server and this orchestration and retrieval stack. It does not predict every production agent workload. Passage length, rerank depth, model latency, tool behavior, validation policy, and operating headroom can all move the boundary.

Included in the measurement

  • One Dell PowerEdge R470 with one Xeon 6761P processor, no accelerator
  • Four complete orchestration instances with 28 executors each, one PostgreSQL database per instance
  • Version-16.1 mix of heavy, medium, and light workflows, with real BM25 search, rank fusion, INT8 cross-encoder reranking on AMX, and context packing on the server
  • Planning, three workers, synthesis, validation, durable tool records, citations checkable against retrieved passages
  • Modeled API-class model waits computed per call from actual payloads (500 ms first token, 100 tokens/s generation, 8,000 tokens/s prompt reading)
  • Three series under different seeds, ten-minute plateaus, offline judgment from evidence records

Outside the measurement

  • Real model generation and provider capacity (latency is modeled; the model tier's own limits are not)
  • The vector index itself (its 15 ms answer is modeled; a large vector database is a separate system)
  • Retrieval quality: capacity is invariant to relevance, so ranking quality is reported as a diagnostic and never judged
  • Production third-party tool services, multi-node coordination, failover
  • Long-duration soak and recovery after overload
  • The exact boundary between 62.7 and the next offered level; depths other than 16 are checked at one seed, not certified

How to use the result. Treat 62.7 workflows per second and about 2,000 resident sessions as the demonstrated capacity of this server for retrieval-backed agents at API-class model speeds, with the reranker sized at 40 cores. A workload that reranks fewer or shorter passages, or fewer times per workflow, will land higher; one that reranks more will land lower, roughly in proportion to rerank calls per workflow. Apply production headroom, then validate the intended model and tool mix before deployment.

08

The result can be traced to versioned evidence

Every submitted workflow produced an evidence record with its type, arrival time, completion time, outcome, offered rate, and host telemetry, including workflows still running when a plateau ended. The versioned plateau judge recomputes every number in this paper from those records, and rule changes are applied to history by re-judging, never by re-running.
