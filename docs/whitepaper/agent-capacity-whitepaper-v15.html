50,000+ AI agents held live on one CPU server

One Dell™ PowerEdge™ R470 sustained 280 complete agent workflows per second while holding more than 50,000 agent sessions in flight at once. Every model call in every workflow waited like a real API call, with the wait computed from the tokens it actually carried.

The CPU ran the orchestration tier: prompt handling, tool dispatch, validation, persistence, and control-plane work. The processor reached 94% before the benchmark stopped, so the figure is the hardware's answer, not the software's.

01

The server held 50,000 agents while completing 280 workflows per second

The four-instance fleet sustained 280.4 complete workflows per second while completions kept pace with arrivals and every model call waited like a real API call. At that rate the server carried about 53,600 agent sessions simultaneously, and every workflow type stayed inside the queued-tier promise: at least 95% finishing within 20 minutes, at 95% confidence, for all three types jointly.

The schedule kept doubling the offered rate until the server itself called time: host CPU held at about 94% while the bounded queue reached its 20,000-per-instance safety cap with roughly 80,000 workflows in flight across the box. The benchmark therefore reports 280.4 workflows per second as the demonstrated sustainable rate, judged offline from the per-unit evidence records.

The session count follows from the rate and the cycle: at 280.4 workflows per second, with workflows running half a minute to several minutes plus a three-second pause, about 53,600 sessions are being served at any moment. Holding sessions is what agents mostly do while models think, and holding them is not free: with instant model responses the same server processed 453.6 workflows per second, so carrying fifty thousand live workflow states costs roughly a third of the orchestration rate. Both facts are measured; the pair is the honest sizing picture.

02

One agent repeatedly completes a defined workflow

An agent session represents one user or process that submits a job, receives the result, pauses for three seconds, and submits another job. A workflow is one completed job. The benchmark keeps every workflow within a fixed work contract so higher load does not quietly reduce the work performed.

Each workflow uses a planner, three specialist workers, synthesis, validation, and durable records. One completed unit contains three subtasks, ten model interactions, seven validation checks, and three tool records. Temporary workers are subagents inside the workflow and do not count as separate sessions.

Every one of the ten model interactions waits like a real API call. The stand-in that answers them computes each call's wait from the tokens it actually carries, using three published serving-tier parameters: time to first token (500 ms), generation speed (100 tokens per second), and prompt-reading speed (8,000 tokens per second). The planner waits longest because it re-reads the whole accumulated conversation on every turn, several seconds a call and growing. Workers wait a few seconds for their assigned slice. Verifier calls wait the least, about a second, because verdicts are short. Nothing is hand-assigned per stage; each wait falls out of the payload, exactly as it would against a production model tier. Tool calls carry their own separate cost: a real durable database write plus 50 to 150 ms of simulated backend latency.

03

The benchmark packed three workflow types across four instances

One load unit contains one research brief, one comparison, and one digest. Adding complete units preserves the same mix at every rate. The approach resembles adding equal groups of marbles to a jar until the jar can no longer accept them at the required pace.

Four complete orchestration instances shared the server. Each instance had one control process, 28 executor processes, one database, and one deterministic model-response router. Splitting the control work across four instances kept one process from limiting the entire server.

The load generator scheduled new workflows independently of earlier completions, doubling the offered rate level by level, with each level held for at least one and a half times the slowest workflow seen so far - several minutes once the research briefs appeared. A rate counted only when completed work kept pace with new arrivals and every workflow type met its deadline.

All of that judging happens after the run, from the per-unit evidence records; the run itself keeps only the stops that protect the server. The reader needs to know that all three workflow types had to pass together, and that a saturated processor or an overflowing queue ended the search.

At the demonstrated rate, the four instances sustained nearly identical confirmed rates of about 70.1 workflows per second each. The 95th-percentile workflow time at that rate was about 8.8 minutes, comfortably inside the 20-minute queued-tier promise.

Past the sustained rate, arrivals outran completions: the processor held near 94% while the bounded queue climbed to its safety cap of 20,000 workflows per instance. The host reached a hardware boundary - most of the box was spent executing workflows and carrying the resident state of tens of thousands more.

05

The result measures orchestration capacity

The CPU performed the work around model calls - building prompts, dispatching subagents, routing requests, validating outputs, writing durable records, relaying events, enforcing budgets - and carried the live state of every waiting session. The benchmark measures the agent host under realistic model timing rather than model generation itself.

A deterministic stand-in returned the planner, worker, synthesis, and judge responses through the production request path, with each response delayed per its payload as described in section 2. Two useful totals fall out of the records: a completed workflow moved about 107,000 prompt tokens and 16,000 generated tokens through its ten calls, so at the sustained rate the model tier behind this host would be absorbing about 30 million prompt tokens and generating about 4.6 million tokens every second - roughly 46,000 concurrent generation streams, which is consistent with the 50,000-session residency. Sizing the inference tier for that demand is the companion question to this paper.

One finding is new and only a realistic run could produce it: residency is not free. With instant model responses this same server processed 453.6 workflows per second; carrying fifty thousand live workflow states cost roughly a third of that rate. Sizing from workflow rate alone, without accounting for resident-session state, overestimates a busy agent host.

06

The capacity figure applies to a defined test boundary

The benchmark establishes a practical starting point for this server and orchestration stack. The result does not predict every production agent workload. Prompt size, model latency, tool behavior, validation policy, persistence, and operating headroom can all move the boundary.

Included in the measurement

  • One Dell PowerEdge R470 with one Xeon 6761P processor
  • Four complete orchestration instances with 28 executors each
  • Version-15 mix of heavy, medium, and light context workflows
  • Planning, three workers, synthesis, validation, and durable tool records
  • Modeled API-class model waits, computed per call from actual payloads (500 ms first token, 100 tokens/s generation, 8,000 tokens/s prompt reading)
  • Controlled tool latency and durable tool records

Outside the measurement

  • Real model generation quality, provider throttling, and network jitter (latency is modeled; provider capacity is not)
  • Production third-party tool services
  • Multi-node coordination and failover
  • Long-duration soak and recovery after overload
  • The exact maximum between the sustained 280.4 and the next offered level

How to use the result. Treat 280.4 workflows per second and roughly 50,000 resident sessions as the demonstrated capacity for context-heavy agents at API-class model speeds, and 453.6 workflows per second as the orchestration-only ceiling with instant responses. Apply production headroom, then validate the intended model and tool mix before deployment.

07

The result can be traced to versioned evidence

Every submitted workflow produced an evidence record with its type, arrival time, completion time, outcome, offered rate, and host telemetry. The versioned sweep judge can recompute the demonstrated rate and session equivalent from those records.
